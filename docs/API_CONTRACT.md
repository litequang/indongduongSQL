# REST API contract — Foundation and Phase 02A/B

The sections below include Foundation, Phase 02A and Phase 02B. Phase 02C endpoints remain absent.

## Phase 02B production

All authenticated reads use no-store and the same current-session authority. Drafts are creator-private. Official production is readable by active users; PRINTER sees only assigned official orders, including history. Production invalidations apply the same scope while advancing the commit cursor over hidden events. Former assignees receive only an opaque deletion invalidation for their previously assigned order, causing their cached view to refetch/remove it; unrelated printers receive no identifier. The client clears private React Query state on session changes.

| Endpoint                            | Contract                                                                                                                                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET /designer-queue                 | Commercial/design roles; server search by product/order/customer, queue status, priority, page/pageSize. Returns exact ordered/allocated/remaining BAG quantity, design revision, technical instruction, note, urgency and queue version   |
| PATCH /designer-queue/:itemId       | Technical roles; `{version,status,instructionRaw,note,isUrgent}`. Status WAITING_DESIGN/NEEDS_INFO/DESIGNING/READY_FOR_PRODUCTION; cannot edit dispatched product; READY requires instruction                                              |
| GET /production-orders              | page/pageSize (max100), search, status, plateStatus, machine, printerId, sort createdAt/code/updatedAt, direction                                                                                                                          |
| GET /production-orders/:id          | Order, production items/allocations, latest 100 history/issues/comments/plate events, latest 50 revisions/cancellations, pending 02C handoffs including superseded marker                                                                  |
| POST /production-orders             | Stable client UUID `id` and productionFields from shared/production.ts. Creates creator-private SQL DRAFT with no LIN code; same actor/id/payload retries return persisted result                                                          |
| PATCH /production-orders/:id        | Full productionFields + version; creator-only DRAFT update. Other windows' changes receive 409                                                                                                                                             |
| POST /production-batches/dispatch   | `{items:[{id,version,requestId}]}`, 1–20 sends, separately committed; `{results:[{id,ok,order? ,error?}]}`. A failed row retains its draft; retry successful rows with the original request                                                |
| POST /production-orders/:id/:action | Every action has `{requestId,version,...actionFields}`; strict unknown-field rejection. Actor/order/action/hash receipt is committed with the write. Same request replays safely; changed payload or actor with the same UUID receives 409 |

Action fields: `dispatch`, `accept`, `wait-print`, `start`, `plate-receive` have no additional fields. `acknowledge` takes exact `revision`. `complete` takes `actualPrintedSheets`, `spoilageSheets` (included in actual, not greater than actual) and optional `note`. `revise` takes full `technical` (raw instruction, paper/GSM/dimensions/color/sheets/machine), active `printerId`, and `reason`. Technical change increments revision; reassignment resets acceptance and ACK. Existing technical imposition sheet totals remain conserved; replacing an imposition requires a new run.

`urgent` takes `isUrgent,reason`; `plate-send` takes optional note; `plate-report` requires reason; `plate-reissue` requires note. `issue-report` takes type PLATE/MACHINE/PRINT/SHIPPING/RETURN/GENERAL, message, optional recipientUserIds/recipientRoles, urgent. Default recipients follow source policy, with creator included for plate issues. `issue-assign` takes issueId and nonempty selected user/role recipients; `issue-resolve` and `issue-cancel` take issueId. Source production issue callables admit seven roles (excluding WAREHOUSE); recipient checks do not bypass that role gate. `cancel-request` takes reason; `cancel-respond` takes cancellationId, boolean accept and reason. `comment` takes content and requires commercial/design or assigned-printer authority. All text/count bounds live in shared/production.ts.

`link-products` takes `{items:[{productionItemId,allocations:[{id,salesItemId,quantity,kind,sourceAllocationId}]}]}` for an existing official item, including after printing. It only appends new links, checks membership/design/conservation, reserves quantity and creates missing handoffs atomically. Numeric late links supersede the old standalone handoff without removing it. Each item’s numeric allocation total equals its product quantity. TRACE is exactly zero. OUTPUT consumes remaining requested BAG quantity. REPRINT requires the original OUTPUT allocation in a PRINTED source run and does not add requested-output quantity. Supplemental/reprint order records require sourceOrderId and runReason.

States implemented: DRAFT → WAITING_ACCEPTANCE → ACCEPTED → optional WAITING_PRINT → PRINTING → PRINTED. Pre-print cancellation is a separate pending request followed by the assigned printer's response. Assigned PRINTER alone accepts/ACKs/starts/completes/responds. Start does not depend on plate readiness or current nonblocking issues. Technical roles cannot revise after print begins. No arbitrary status-patch endpoint exists.

Completion returns `PENDING_02C` handoffs, never stock or a completed finishing task. A no-finishing product still needs the future explicit no-work checkpoint. Print-image metadata has no upload bytes/URLs and registry IDs remain unavailable until Phase 03.

Same-origin `/api`, JSON only, UTF-8. Every response is `Cache-Control: no-store, private`. No CORS credentials. Error body: `{ "error": { "code": "VERSION_CONFLICT", "message": "..." } }`; validation adds field paths/messages. 400 invalid input, 401 unauthenticated, 403 authority/Origin/CSRF failure, 404 absent endpoint/entity, 409 duplicate/stale version/bootstrap completed, 413 body >64 KiB, 415 non-JSON mutation, 429 rate limit, 503 bounded password worker overload/readiness. No stack, SQL, hash or secret is returned.

All POST/PATCH require exact configured `Origin`. Authenticated mutations additionally require `X-CSRF-Token` from login or `/auth/me`. Cookie is HttpOnly, SameSite=Lax, Path=/, Secure and `__Host-idd_session` name in production; dev/test uses `idd_session`. Auth tokens never appear in response JSON or browser storage. Absolute session lifetime defaults to 12 hours. CSRF value is memory-only in frontend.

User DTO: id, username, name, phone, role, machineAssigned, active, version, createdAt, updatedAt. No password hash, email identity mapping or PIN. Username uses 3–64 lowercase ASCII letters/digits/dot/underscore/hyphen; passwords 12–128 characters on creation/change/reset. Unknown request fields are rejected. Each settings field/options/threshold is validated by server/validation.ts; primary colors are a contrast-reviewed palette.

Settings DTO: companyName, shortName, phone, address, website, slogan, primaryColor, acceptanceMinutes, plateMinutes, printingMinutes, pollIntervalMs (3000–30000), printers, paperTypes, colors, finishingTypes, version. Lists max50 unique entries, max100 characters each. Missing data is not silently written locally.

Change events contain sequence, entity(users/settings), entityId, version, deleted. The feed carries invalidations/tombstones only, no universal private payload. Read current bounded endpoint after invalidation. Phase 01 retains events without pruning; future retention requires an explicit cursor-expired/full-refresh protocol. Every publishing mutation takes system_state lock first and retains it through commit, avoiding late-commit gaps. Stale writes receive 409 and must be reviewed/reloaded, never silently retried as a merge.

Production business, image upload, JSON-store sync, AI, bulk overwrite and old unauthenticated `/orders`/`config` APIs are absent. Unfinished UI modules cannot issue a successful fake mutation.

## Phase 02A business API

Authentication, Origin, CSRF and no-store follow the existing contract. Error codes for actionable business conflicts include `CUSTOMER_DUPLICATE`, `VERSION_CONFLICT`, `INVALID_STATUS`, `REQUEST_CONFLICT` and `IMPORT_BATCH_ORDER`. Normal bodies are bounded to 64 KiB. Sales create/update and import staging accept up to 512 KiB of uncompressed JSON after Origin verification. Shared DTO and input schemas live in `shared/business.ts`. Unknown fields, including caller-supplied stage, role, owner, stock, print sheets or image data, are rejected.

Lists use `page` (default 1), `pageSize` (default 20, maximum 100), and where documented `direction=asc/desc`. Customer ID links resolve on the backend. Customer updates preserve their import provenance. Quantities count individual BAG units. A design response reserves nullable `image: { registryId }`. Current designs return `null` for images.

`GET /changes` adds invalidations for `customers`, `sales_orders` and `saved_designs`. Customers send a tombstone on retirement. Customer/sales/design events contain opaque entity IDs and versions and use the same authenticated read scope as their endpoints. Import jobs are actor-scoped and are excluded from the global feed.
